2. **`CONCAT_VEP` and `MERGE_ANNOTATIONS`**: each first attempt was killed at the `process_single` 1 h limit, the MISC-16 mitigation. Their successful retries took 1.07 h and 1.38 h at ~100% of one core. At WGS size these tasks can never finish on attempt 1, which costs ~2.2 h of wall time. The cause is **not determined**. Three changes happened between the runs:
   - `c77072b` changed both commands (concat piped into sort, BCF intermediates in merge);
   - the work dir moved to `/mnt/scratch` (2026-10-08);
   - bcftools sort temp files moved from the node's `/data_tmp` into the task dir (`e1ad046`).
3. **`TSV_TO_TABLE`**: attempt 1 (4 slots, `memory` 48 GB, `h_vmem=58G`) failed with `pandas ... C error: out of memory`. Attempt 2 (8 slots, 72 GB, `h_vmem=82G`) succeeded in 38 min. This answers the open per-slot/per-job question of the 2026-10-14 review, still to be confirmed with `qconf -sc`. The `memory` / `h_rss` / `mem_free` request (72 GB) understates real use by about 4.5x, so the scheduler can over-commit a node.
4. **`TAG_TRANSCRIPT_PRIORITY`**: attempt 1 succeeded, 2.5 min, peak 13.5 GB of 24 GB. F2005 needed 6 attempts. The 2026-10-14 check passes.
5. **VEP / SPiP**: 86.7 / 72.4 task-hours vs 62.4 / 53.6. VEP now includes ReMM (expected; not comparable).

### Why `CONCAT_VEP` takes 1 h (2026-10-30)

The retry's `.command.trace`: 64 min at ~100% of one core, rchar 45 GB, wchar 40 GB; `bcftools sort` merged 16 temporary files. The 263 chunks hold ~37 GB of VCF text (~7 KB per record, from VEP's CSQ). Local timing on 26 of the 263 chunks (269 MB compressed, 520,000 records, bcftools 1.21, page cache warm):

| Step | Time |
|---|---|
| index each chunk (`tabix`) | ~5 s |
| `concat -a` alone | 16 s |
| `concat -a \| sort -Ou` | 41 s |
| `concat -a \| sort -Oz` (current) | 98 s |
| `tabix` of the output | 8 s |
| chunks ordered by first record, `concat --naive` + `tabix` | 7 s |
| same order, `concat --threads 4 -Oz -W` | 15 s |

FACT: ~60% of the current time is writing compressed VCF text in one thread, ~25% the sort, ~15% parsing. The chunks of the broad tier are disjoint position ranges of the sorted input, so the sort only repairs the order in which Nextflow hands them over. Ordered `--naive` (copies the compressed blocks; header compatibility checked, it accepts the per-chunk VEP `time=` lines) gives the same records as the current output (sorted text md5 equal); 608 of 520,000 records differ in order, all at a position shared by several alleles, where the naive output keeps the input order and `sort` reorders them.

INFERENCE: ~15x faster, so `CONCAT_VEP` would take a few minutes on a WGS.

**Applied 2026-10-30 (Mario)** in `CONCAT_CHUNKS` (`modules/local/chunk.nf`): chunks are ordered by their first record (contig rank in the header, then POS; header-only chunks left out) and joined with `concat --naive`; `tabix` of the output refuses records out of order, so a failure means the chunks overlapped, and the task falls back to `concat -a | sort`. `--naive` also stops when a chunk lacks a header tag that another has (tested), which falls back the same way. The record-count parity check is unchanged. Checks:
- Local `-stub-run` (`local_dev`, bcftools 1.24, `clinvar_af_fixture`, `--chunk_size 5`): every `CONCAT_*` joined in position order, `annVEP` records identical to the input. With a test score cache holding 2 of the 5 gene-region sites: `CONCAT_SPLICEAI`/`CONCAT_PANGOLIN` took the fallback, the others the ordered path; parity passed everywhere.
- The rendered script on all 263 real `annVEP` chunks of `F1830_union_avi` (cluster bcftools 1.21, read from `/mnt/scratch`, output in the session scratchpad): 130 s, 119 MB RSS. 5,255,129 records; with records sorted inside each position, md5 equal to the published `annVEP`; record order (CHROM:POS:REF:ALT) identical to the input VCF. Output 2.69 GB vs 2.51 GB (VEP's own bgzip blocks are kept).
- `bcftools annotate -a` (as in `MERGE_ANNOTATIONS`) matches alleles at one position whatever their order in either file (synthetic test, bcftools 1.21).

Cluster fixture `concat_fixture_1` (2026-11-03, `814ab97` clean, `--chunk_size 5 --gene_restricted_chunk_size 2`, test cache `/mnt/scratch/mruizp/annotation_cache_test`): exit 0, 29 tasks, 0 failed; every `CONCAT_*` joined in position order (VEP and Branchpoint 5 chunks, SPiP 3), parity passed; SpliceAI/Pangolin 5/5 cache hits. Final table vs `cache_fixture_2`: 199 x 586, same rows in the same order; differences only in `5UTR_annotation` key order (2 rows, known) and SPiP number formatting (87 values, all equal within 1e-6 relative; SPiP prints with per-chunk precision, and this run had 3 SPiP chunks instead of 1). The fallback did not run on the cluster (all-hit cache).
