- [ ] **Incremental re-annotation: re-annotate an already-annotated file with only the new/changed annotators, instead of re-running the whole pipeline** (Mario, 2026-10-01; not yet designed)
  - Motivation: the pipeline is under active iteration (bug fixes, new predictors/annotators — see Phase 2 candidates). Today any change forces a full re-run of a file that is otherwise almost entirely annotated, which for WGS-scale inputs costs days of SpliceAI/Pangolin inference.
  - **Open design questions (to resolve before implementing):**
    1. **Validity of existing annotations** — how to prove a previous output is reusable: same tool/model/database versions as the current config, same parameters (e.g. SpliceAI `-D`, VEP cache/`--pick` flags, consequence/AF filters), same reference FASTA/assembly. Natural source: the per-run manifest (`write_run_manifest.py`, Nextflow entry point only; `main.sh` has none — see Priority 0 provenance item, which this depends on). Annotations from a run with no manifest = unknown provenance → not reusable without explicit override.
    2. **Region/variant coverage** — confirm the prior run covered the same regions (gene restriction BED, chunking, filters that dropped variants) and the same variant set as the new input; define what happens to variants present now but absent before (annotate fully) or the reverse (drop/flag).
    3. **Which annotators need re-running** — per-predictor staleness decision (new predictor → run only it; version/parameter change, e.g. SpliceAI `-D 10000`→`4999` or the `PLT-139` Pangolin db fix → re-run only that predictor and invalidate its old columns). Must never leave stale columns from an old version silently alongside fresh ones.
    4. **Input format for the re-run** — feed the previous annotated output back in as input. Options to evaluate: (a) keep the annotated VCF and add only the new INFO/CSQ fields (VCF-native, lossless for what's already in it, but tools like VEP re-emit/append to existing CSQ and need care to avoid duplicate/clobbered fields); (b) convert the parsed `.pq`/TSV back to VCF (`universal_variant_converter.py` goes the other direction in practice — check whether a lossless round trip exists; the parsed table is likely lossy for multiallelics/raw INFO); (c) use the old output only as a lookup keyed on CHROM/POS/REF/ALT and join the new annotators' results onto it. Prefer whichever preserves the native VCF as authoritative input (global rule: native formats are authoritative; parsed tables are derived).
    5. **Provenance of the merged result** — the new manifest must record, per annotation column, which run/version produced it (mixed-lineage output), and link back to the parent run.
  - **Depends on**: the run provenance manifest, already available for `annotate_vcf.nf` (the `main.sh` manifest is no longer planned: bash path deprecated 2026-10-02). Variant identity must be normalized (left-aligned, split multiallelics) the same way in both runs or the join silently drops/duplicates records.
